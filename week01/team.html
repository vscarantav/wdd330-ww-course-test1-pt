S01 – Projeto: Atividade S01: Configuração do Projeto da Equipe

Visão Geral

Esta atividade é a configuração e o início do projeto da equipe. Você não precisará se reunir sincronicamente esta semana com sua equipe, mas é altamente recomendável que tente fazer isso.

Normalmente, você designará um membro da equipe como o "piloto principal" e colaborará na cópia do código do piloto durante as reuniões síncronas para Atividades em Equipe. O piloto deve ser o único a digitar o código, o restante da equipe orienta o piloto e ajuda a concluir as etapas, incluindo a escrita do código.

Instruções da Atividade

Sua equipe terá um quadro do Trello e um repositório oficiais do projeto.

    Ajuda: Capturas de tela

    Lembre-se de continuar adicionando membros à medida que eles se juntarem à equipe.

    Ajuda: Capturas de tela

    Ajuda: Captura de tela

Configuração do Projeto – Clonar Repositório

  1. Faça login no GitHub e clone este modelo de repositório do Sleep Outside clicando no botão "Use this template" para criar uma cópia do projeto em um novo repositório e dar um nome ao novo repositório.
  2. Acesse o repositório clonado Settings > Manage Access e adicione o restante dos membros da equipe como colaboradores.

Clonar e Compilar o Projeto

  1. Todos os outros membros da equipe precisam clonar este repositório da equipe para seus próprios computadores.
  2. No VS Code, abra o diretório que contém o repositório clonado.
  3. Abra uma janela do terminal e mude para o diretório do projeto.

    Abra o terminal no VS Code pressionando ctrl+~ para alternar o painel do terminal entre aberto e fechado.

    No VS Code, você pode usar o painel do terminal (ctrl+~ alterna o painel do terminal entre aberto e fechado). Quando você abre o terminal no VS Code, ele será definido automaticamente para a raiz do seu projeto.

  4. Execute o comando de listagem da interface de linha de comando (ls) ou diretório (dir) para listar todo o conteúdo do diretório/pasta atual. Certifique-se de ver o package.json na lista de arquivos. Mude para o diretório correto do projeto clonado se não vir esse arquivo.
  5. Execute a rotina de instalação do gerenciador de pacotes do node usando o terminal. 
    >npm install
  6. Observe que um novo diretório foi criado: node_modules
  7. Este projeto vem com várias ferramentas integradas para ajudar a equipe a escrever um código consistente e sem erros.
    Abra o arquivo package.json. Há duas seções para analisar inicialmente, devDependencies e scripts.
    • devDependencies contém todas as ferramentas necessárias para o desenvolvimento deste projeto. A execução do npm install consultou esta lista para saber o que instalar.
    • scripts são atalhos para comandos de gerenciamento do projeto. Ele contém o seguinte 
         "scripts": {
  "start": "vite",
  "build": "vite build --emptyOutDir",
  "lint": "eslint *.js src/**/*.js",
  "format": "prettier --ignore-path ./.gitignore --write \"./**/*.{html,json,js,ts,css}\"",
  "test": "jest"
  },
      • start: Isso executará o servidor de desenvolvimento. Você usará isso com mais frequência.
      • build: Isso preparará o código para ser implantado em produção. Uma pessoa da sua equipe deve ser designada para executar isso conforme necessário.
      • lint: Isso executará o ESLint no código para procurar erros de estilo e sintaxe. Você deve fazer isso toda vez que estiver pronto para fazer o commit. Certifique-se de corrigir quaisquer erros encontrados antes de fazer o commit!
      • format: Isso executará o Prettier no seu código e o formatará de maneira consistente. Você também deve fazer isso como uma etapa do seu processo de commit.
      • test: Isso executará o framework de testes Jest no seu código.

      Os comandos são executados no terminal. Se você quisesse iniciar o servidor de desenvolvimento, por exemplo, digitaria npm run start no terminal. Se quisesse executar o linter, digitaria npm run lint.

  8. Tente executar o linter agora. 
    >npm run lint
    O que você viu? Abra o arquivo .eslintrc.json. Você pode ter notado que um dos erros relatados é que suas aspas deveriam ser todas simples.

    As aspas precisam ser aspas simples? Isso importa? Na verdade, não importa se você usa aspas simples ou duplas em seu código JavaScript. No entanto, é importante ser consistente. Sua equipe precisará concordar com um padrão e segui-lo. É por isso que o linter é usado para impor um padrão. Ele ajudará você a evitar erros e tornará seu código mais legível.

  9. Decidam em equipe se gostariam de usar aspas simples ou duplas. Em seguida, encontre a linha parecida com esta: "quotes":["error", "single"] no arquivo .eslintrc.json. Se você quiser aspas simples, não faça alterações. Se quiser aspas duplas, mude a palavra "single" para "double".

    O arquivo eslintrc.json pertence à equipe. Se a sua equipe discordar de alguma das regras que estão sendo impostas, altere-as. Apenas certifique-se de que todos os membros da equipe concordem com as alterações. Se você decidir se aprofundar na configuração de regras personalizadas do ESLint, pode ser útil obter a extensão LintLens para o VSCode.

  10. Execute o seguinte comando: 
    >npm run format
    Em seguida, execute o linter novamente. O que aconteceu? Peça a alguém para corrigir quaisquer erros restantes e, em seguida, faça o commit e envie as alterações.

    Cada membro da equipe deve executar os comandos format e lint antes de fazer o commit após realizar qualquer alteração ao longo do curso.

  11. Execute o seguinte comando: 
    >npm run start
    Isso executa vários processos no código e inicia um servidor web em localhost:xxxx onde xxxx é o número de alguma porta. Ele também deve abrir esse endereço no seu navegador padrão; se isso não acontecer, você pode digitar esse endereço diretamente no navegador ou clicar no link no terminal.

    Você deve usar este servidor ao desenvolver seu projeto em vez de algo como o Live/Five Server.

  12. Quando terminar de trabalhar, você pode parar o servidor dev digitando ctrl c na mesma janela do terminal em que o processo está em execução. Isso o encerrará.

Publicação

  1. Gere a compilação de distribuição usando o seguinte comando: 
    npm run build
    Isso criará um diretório chamado dist.
  2. Apenas uma pessoa precisará fazer o commit dessas alterações e enviá-las para o GitHub.
  3. Veja o repositório em github.com e observe que o dist diretório não foi transferido com o commit. Se você verificar o .gitignore arquivo que faz parte do projeto, você verá o porquê.
  4. Você usará uma plataforma chamada Render para hospedar o site da aplicação web em execução.
    ✔ Crie uma conta gratuita no Render usando suas credenciais do GitHub e faça login para a próxima etapa.
  5. Após fazer login, você precisa adicionar um novo Site Estático. Clique no botão "+ New" na parte superior e selecione GitHub.
  6. Selecione o repositório que contém o sleepoutside projeto.
  7. Selecione a branch "main" e confirme estas configurações antes de implantar:
    • Comando de Compilação: npm install && npm run build
    • Diretório de Publicação: dist
    Depois, Implantar Site Estático. O Render gerará uma URL aleatória para o site que deve ser compartilhada com todos os membros da equipe.
    Este é o link para o seu site de "produção".

    ✔ A versão de compilação do site será considerada a versão de produção. Este site de aplicativo deve sempre estar funcionando. O Render atualizará seu site toda vez que detectar uma alteração na branch "main" do GitHub. Portanto, após os pull requests serem revisados e mesclados, você provavelmente deve acessar a URL do Render para garantir que nada tenha quebrado.

Conflitos de Mesclagem

  1. Puxe as alterações do GitHub.
  2. Se ele ainda não existir, crie um arquivo na raiz do projeto chamado team.txt.
  3. Certifique-se de que haja um link para o quadro do Trello da equipe no arquivo de texto.
  4. Adicione o seu nome ao arquivo de texto.
  5. Em seguida, faça o commit dessa alteração e envie -a para o GitHub.
  6. O que aconteceu? Isso deveria ter resultado em um erro no Git se mais de uma pessoa tiver editado, feito commit e enviado o arquivo.

    Foram feitas várias alterações no mesmo arquivo e o Git não sabe qual delas manter. Isso resulta em um conflito de mesclagem. Como os conflitos podem ser evitados? De algumas maneiras:

    • Primeiro, certifique-se de que, sempre que se sentar para trabalhar no projeto, você faça um pull antes de fazer qualquer outra coisa para garantir que obtenha as alterações que qualquer um dos seus companheiros de equipe tenha feito recentemente.
    • Faça commits com frequência! Commits pequenos têm menos probabilidade de resultar em conflitos do que os grandes... e são muito mais fáceis de corrigir se ocorrer um conflito.
    • Aproveite as técnicas de design de software como módulos para dividir seu código em partes menores.
    • Por fim, aproveite a capacidade do Git de criar branches. O uso de branches é introduzido no desafio adicional desta atividade abaixo.
  7. Antes de poder fazer o commit, o conflito de mesclagem precisará ser resolvido. Certifique-se de que o arquivo team.txt esteja aberto. Você deve ver algumas adições ao arquivo feitas pelo Git. Deve se parecer com algo como abaixo.

    Você deve decidir qual código deve ser mantido.

    • O conteúdo do código sob o <<<<<<<•HEAD é o código que você estava tentando enviar.
    • O conteúdo do código sob o ======= é o código que já estava no GitHub.
    • Se quiser manter o código que acabou de escrever e descartar o outro, escolha "Accept Current Change".
    • Se quiser manter o que estava no GitHub e remover suas alterações recentes, escolha "Accept Incoming Changes".
    • Ou, se você escolher "Aceitar Ambas as Alterações", isso irá mesclar ambos os conjuntos de alterações. Esta é frequentemente a maneira mais rápida de se livrar do conflito, mas geralmente exige mais trabalho para realmente corrigir o problema.
    • Neste caso, aceite ambas e, em seguida, exclua o nome sem a inicial. Isso nos deixaria com as versões mais atuais de tudo.
  8. Assim que corrigir o código, você precisará fazer o commit da mesclagem.
  9. Envie suas alterações para o GitHub.

Esta foi uma mesclagem simples, pois foi fácil ver o que precisava ficar. Imagine se o arquivo tivesse 200 a 300 linhas de extensão e dois membros da equipe tivessem feito edições em 10 a 15 linhas de código espalhadas pelo arquivo e causado um conflito de mesclagem. Teria sido muito mais difícil descobrir o que manter. A lição é manter seus commits pequenos.

Desafio Adicional

Uma das funcionalidades mais poderosas do Git é a capacidade de criar branches do código. A criação de branches faz uma cópia do código do projeto no momento atual em que as alterações são feitas, sem afetar qualquer outra branch. Isso permite que uma organização mantenha sempre uma versão de produção totalmente funcional do código da aplicação que pode ser implantada a qualquer momento, enquanto também trabalha em atualizações que normalmente causariam uma interrupção no serviço da aplicação.

Você também pode usar branches para reduzir conflitos de mesclagem se vários membros da equipe precisarem fazer alterações no mesmo arquivo em uma base de código.

Instruções de Prática de Branching

  1. Crie uma nova branch. Dê à sua branch um nome como yourinitials--branch-test.
  2. Adicione um arquivo na raiz do projeto chamado seunome.txt.
  3. Digite seu nome no arquivo de texto e salve-o.
  4. Faça o commit e publique (envie) sua branch para o GitHub.
  5. Conclua um pull request depois que todos os outros membros da equipe tiverem enviado suas próprias branches.
  6. Alterne para uma das novas branches no repositório. Observe o que acontece com a lista de arquivos no seu editor quando você faz isso.
  7. Volte para a sua própria branch.
  8. Volte para a branch main.
  9. Discuta com sua equipe o que você viu.

Ao longo do semestre, você estará corrigindo bugs e adicionando funcionalidades ao projeto SleepOutside. Quando você atribuir uma tarefa a si mesmo, crie uma nova branch para conter o trabalho que irá fazer. Dê à branch o nome initials--feature-name. Em seguida, quando tiver concluído seu trabalho e estiver confiante de que tudo está funcionando, envie um pull request.

Pull Requests

Quando você terminar a funcionalidade para a qual criou uma branch, o novo código deve ser mesclado de volta na branch main. Isso pode ser feito de duas maneiras:

  • mesclando diretamente a branch de trabalho de volta na branch main, ou
  • executar um pull request.

Em projetos onde há apenas um desenvolvedor, mesclar diretamente funciona. No entanto, ao trabalhar com uma equipe, é mais comum trabalhar por meio de pull requests. Um pull request significa essencialmente "Meu trabalho está concluído e testado, estou pronto para que o código seja mesclado com a branch main. Alguém pode verificar e garantir que não vê nenhum problema? (Para eu não quebrar nada 😁)"

Neste caso, no momento, as branches não contêm nada importante que precise ser mesclado de volta na branch main. Portanto, a maioria delas pode ser simplesmente excluída.

  1. Peça a uma pessoa da equipe, que não seja o piloto (driver), que envie um pull request para sua própria branch para observar como é o processo.
  2. Após a criação do pull request, o piloto deve ir ao repositório no GitHub, revisar a requisição e, em seguida, finalizar a mesclagem.
  3. Certifique-se de que todas as branches extras sejam excluídas assim que a mesclagem for concluída.
  4. Mova o cartão Team Activity S01 no Trello para "Done".
